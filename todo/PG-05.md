## PG-05 — Extension-aware handling and per-extension UI

- **Status:** done
- **Depends on:** PG-01

### Goal

Popular extensions change what a database *is*. Detect them and adapt.

### Acceptance criteria

- [x] The Extensions node lists installed extensions with version, schema and
      whether a newer version is available.
- [x] Available-but-not-installed extensions are listed separately.
- [x] Install/update/drop actions with a confirmation showing the SQL, gated on
      privileges.
- [x] A registry maps known extensions to behaviour, starting with: **PostGIS**
      (hands off to PG-04), **pg_stat_statements** (feeds CORE-15), **TimescaleDB**
      (hypertables and chunks in the tree), **pgvector** (vector column display),
      **pg_cron** (job list), **uuid-ossp**/**hstore**/**citext** (type-aware
      display only).
- [x] Extension-owned objects are attributed to their extension in info views
      rather than appearing as mysterious user objects.
- [x] Unknown extensions get the generic listing — no errors, no special-casing
      required to function.

### Note

Scope this down at implementation time if it's too big; the registry plus the
Extensions node is the minimum viable slice, the per-extension UIs can each
become their own follow-up ticket.

### What landed

The minimum viable slice the note allows, plus the attribution:

* `backend/db/extensions.py` — the registry (traits, features, types)
  and the CREATE/ALTER/DROP EXTENSION builders;
* one listing (`Connector.list_extensions`) behind the Extensions and
  Available Extensions folders, with version, schema and "update to";
* install/update/drop from the row's context menu, statement shown,
  gated on `can_manage_extensions()`;
* PG-04's PostGIS check re-expressed as the registry's `spatial`
  feature, so there is one mechanism and not two;
* extension-owned objects attributed in the info views.

Deferred to follow-up tickets, as the note allows — the registry
already declares which extension brings which, so each hangs off a
feature flag rather than a new mechanism: TimescaleDB hypertables and
chunks in the tree, pg_cron's job list, and vector/hstore/citext
column rendering in the grid.
