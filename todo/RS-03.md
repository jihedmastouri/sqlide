## RS-03 — Research: BI / charting support

- **Status:** done — research complete, follow-ups filed

### Questions to answer

- Scope: chart a result set (small, achievable) vs saved dashboards vs a full BI
  tool. Where do we stop, given this is a database client?
- Chart types worth supporting for a v1, and how columns map to axes/series
  (auto-detected from result types, or user-configured?).
- Where charts live: a tab on the results pane, or separate saved objects?
- Saving/exporting: PNG/SVG export, chart definitions stored in config (CORE-13)
  so they're git-friendly, refresh-on-rerun.
- Data volume: aggregate in SQL, or in the client? What's the row cap?
- Does this overlap enough with PG-04's map view to share infrastructure?
- Which charting library, and does it fit the app's licensing and bundle size?

### Deliverable

- [x] A short written proposal with a scoped v1, and follow-up tickets created
      from it.

### Outcome

Written up in `docs/charting-research.md`. The direction: chart the
result set, not the database — a serialisable `ChartSpec` in
`backend/charts.py`, drawn with cairo ourselves (no charting library:
matplotlib would add ~100 MB and numpy, and would not follow the
libadwaita theme), shown as a third view in the tab stack beside Data,
Properties and Map. `metrics.Chart` and the monitoring dashboard stay
as they are; only the drawing primitives are shared, with
`_ChartCard._draw` rewritten onto them. Follow-ups: CORE-30 … CORE-35.
