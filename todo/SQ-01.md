## SQ-01 — SQLite sidebar tree: full node set

- **Status:** done
- **Depends on:** CORE-01, CORE-02

### Target tree

```
Connection
├── Tables
│   ├── Columns
│   ├── Keys
│   ├── Foreign Keys
│   ├── Constraints
│   ├── Indexes
│   ├── References
│   └── Triggers
├── Views
├── Indexes
├── Functions
├── Sequences
├── Table Triggers
└── Data Types
```

### Acceptance criteria

- [x] The tree matches the structure above; no database or schema level for the
      main database (but `ATTACH`ed databases, if supported, appear as siblings).
- [x] Every node opens an info view (CORE-01).
- [x] SQLite realities are handled honestly rather than faked: "Sequences" means
      `sqlite_sequence` for AUTOINCREMENT tables and is empty/hidden when absent;
      "Functions" lists built-in and registered functions and is clearly marked
      read-only; "Data Types" reflects storage classes and type affinity, not a
      user-defined type catalog.
- [x] Internal `sqlite_*` objects are dimmed, consistent with PG-03.
- [x] Both "Indexes" under a table and the top-level "Indexes" node work, without
      duplicating implementation.

### Notes

- The three awkward folders are kept, each as the thing SQLite
  actually has rather than an imitation of another engine's:
  - **Functions** is `pragma_function_list` — the functions the
    library was built with plus any the process registered — read-only
    on every row (there is no CREATE FUNCTION, so the sidebar offers
    neither Edit Definition nor Drop, both gated on `ddl_kinds`). An
    older library with no such pragma falls back to the core built-ins
    rather than an empty folder. Functions used to hold this engine's
    *triggers*; they now have a folder of their own.
  - **Sequences** is `sqlite_sequence`, one row per AUTOINCREMENT
    table saying which rowid it last used. A file that declared no
    AUTOINCREMENT has no such table and the folder is empty.
  - **Data Types** is the five storage classes and the affinity rules
    around them — the same declaration the table designer offers
    (`column_type_specs`), so there is one list, not two.
- "Table Triggers" is the tree's own word for the shared `triggers`
  folder (`CATEGORY_LABEL_OVERRIDES`): a trigger here always belongs to
  a table, and the table's own Triggers section sits right under it.
- "Keys" is a new Properties section (`keys`) behind a capability flag
  of the same name, filled from the constraint listing Constraints
  already shows — the primary key and the unique ones, with the
  foreign keys left to the section that is about references. SQLite is
  the only engine that turns it on.
- `sqlite_*` objects are listed instead of filtered out of
  `list_tables`, and the provider's `is_system_object` marks them, so
  the sidebar dims and sorts them last exactly as it does a system
  schema (PG-03). That question is new at this layer: the engines with
  schemas keep their internals in one, and answer False.
